# Просмотры статей

## Что считается просмотром

Просмотр — это один уникальный IP-адрес для одной статьи. Повторные открытия той же статьи с того же адреса не меняют счётчик.

Статья может иметь несколько локализаций, но для просмотров это один материал. Поэтому чтение `/en/articles/example` и `/ru/articles/primer` одним человеком даёт один просмотр: обе локализации привязаны к одному `ArticleId`.

Счётчик показывается на странице статьи рядом с датой публикации. Он пока не выводится в списках статей, темах или сериях.

## Путь запроса

```text
Браузер
  │  GET /api/public/articles/{language}/{slug}
  ▼
API возвращает статью и текущее число просмотров
  │
  │  POST /api/public/articles/{language}/{slug}/views
  ▼
API определяет клиента, пытается сохранить уникальный просмотр
  │
  ▼
API возвращает актуальный ViewCount
  │
  ▼
Браузер обновляет число рядом с датой статьи
```

Получение статьи через `GET` ничего не записывает. Регистрация вынесена в отдельный `POST`, чтобы простое чтение API, предварительная загрузка и большинство поисковых роботов не меняли статистику.

Если запрос регистрации не прошёл, статья всё равно открывается. На экране остаётся значение, полученное вместе со статьёй.

## Как API получает IP посетителя

В production запрос проходит два proxy:

```text
клиент → host nginx → web nginx → API
```

Каждый nginx дописывает адрес предыдущей стороны в `X-Forwarded-For`. API запускает обработку forwarded headers раньше rate limiting, авторизации и контроллеров.

API доверяет этому заголовку только если непосредственное соединение пришло из сети, заданной в `ForwardedHeaders:TrustedNetworks`. Это принципиально: клиент может сам прислать заголовок `X-Forwarded-For`, но он не должен получать возможность выбрать себе IP.

`ForwardLimit` равен `2`, потому что между клиентом и API ровно два доверенных proxy. Обработчик читает цепочку справа налево: сначала web nginx, затем host nginx, затем получает реальный адрес клиента.

## Как IP становится безопасным идентификатором

Сырой IP в БД не хранится. Перед записью API:

1. Приводит IPv4-mapped IPv6 к обычному IPv4. Это не даёт одному посетителю считаться дважды из-за формата адреса.
2. Вычисляет `HMAC-SHA256(IP)` с секретом `Analytics:ViewHashKey`.
3. Сохраняет только 64-символьный шестнадцатеричный результат.

HMAC позволяет сравнивать повторные визиты, но без секрета нельзя заново получить значение для произвольного IP. Это всё ещё псевдонимизированные аналитические данные, а не полностью анонимные: к ним нужно относиться как к данным статистики и не публиковать их.

Секрет должен быть стабильным. После его смены хеши для тех же IP изменятся, и старые посетители начнут считаться новыми. Ротацию ключа следует проводить только осознанно, понимая, что это разрывает историю уникальности.

## Хранение в БД

Таблица `article_views` содержит:

| Поле | Назначение |
| --- | --- |
| `ArticleId` | Статья, а не её отдельная локализация |
| `VisitorHash` | HMAC-SHA256 от нормализованного IP |
| `FirstViewedAt` | Когда этот посетитель впервые открыл статью |

Первичный ключ — пара `(ArticleId, VisitorHash)`. Он одновременно даёт быстрый подсчёт по статье и не позволяет сохранить один и тот же просмотр дважды. При удалении статьи её записи просмотров удаляются каскадно.

Вместо отдельного изменяемого поля-счётчика API считает строки `article_views`. Это избавляет от риска, что число на статье и реальные записи когда-нибудь разойдутся. Для текущего объёма данных это простое и надёжное решение.

## Защита от одновременных запросов

Несколько вкладок могут открыть страницу почти одновременно. Проверка «есть ли уже такой просмотр» перед вставкой была бы ненадёжной: обе вкладки могли бы увидеть, что записи ещё нет.

Поэтому PostgreSQL получает один атомарный запрос:

```sql
INSERT INTO article_views ("ArticleId", "VisitorHash", "FirstViewedAt")
VALUES (...)
ON CONFLICT ("ArticleId", "VisitorHash") DO NOTHING;
```

Один запрос вставит строку, остальные спокойно ничего не сделают. Затем API возвращает актуальное число строк для статьи.

## Конфигурация production

В `deployment/.env` должны быть заданы значения:

```dotenv
# Случайная строка не короче 32 байт. Не менять без необходимости.
GAIFULINLAB_ANALYTICS_VIEW_HASH_KEY=...

# Реальная CIDR-подсеть Docker-сети, соединяющей web и API.
GAIFULINLAB_FORWARDED_HEADERS_TRUSTED_NETWORK=172.18.0.0/16
```

Второе значение нельзя слепо копировать из примера. Его нужно взять из вывода:

```bash
docker network inspect gaifulinlab-host-nginx
```

Если ключ HMAC отсутствует или короче 32 байт, API не запускается. Если не задана доверенная сеть proxy, API также не запускается: безопаснее явно исправить конфигурацию, чем принять поддельные адреса.

## Ограничения выбранной модели

- Пользователи за одним NAT, корпоративной сетью или VPN могут считаться одним посетителем.
- У пользователя с динамическим IP может появиться несколько просмотров.
- Автоматизированный клиент, который сознательно вызывает `POST /views`, может создать просмотр. Это не антифрод-система.
- При росте трафика можно добавить ограничение частоты, агрегацию или отдельный аналитический контур. Текущая модель намеренно проста.

Для публичного счётчика статей эти ограничения приемлемы. Когда появятся зарегистрированные пользователи, лайки будут отдельной сущностью с уникальностью по `ArticleId + UserId`; они не связаны с IP-подсчётом просмотров.

## Проверки

Покрыты тестами первый и повторный просмотр, разные посетители, общность счётчика между локализациями, черновики, forwarded headers, отображение в UI и 16 конкурентных запросов на PostgreSQL от одного посетителя.
