## 1. P1 — блокировка пользователя не препятствует выдаче JWT

Код: [UserAuthenticationService.cs](../src/GaifulinLab.Infrastructure/Authentication/UserAuthenticationService.cs), строка 19; [Program.cs](../src/GaifulinLab.Api/Program.cs), строка 31.

`AuthenticateAsync` вызывает `FindByNameAsync` и `CheckPasswordAsync`, затем выдаёт JWT. Проверки `IsLockedOutAsync` нет, неудачные попытки не увеличивают `AccessFailedCount`. Rate limit привязан только к IP и не заменяет блокировку учётной записи.

Воспроизведено: включить `LockoutEnabled`, установить `LockoutEnd` на следующий день, проверить `IsLockedOutAsync == true`, затем выполнить login с правильным паролем. Результат — 200 и токен. Это позволяет продолжать вход под заблокированной учётной записью; распределённый подбор пароля не ограничивается на уровне пользователя.

Исправление: использовать проверку входа Identity с учётом lockout либо явно реализовать проверку блокировки, учёт неудач и сброс счётчика после успеха. Проверить сценарии блокировки и повторного входа интеграционными тестами.

Один аккаунт может многократно отправлять допустимые изображения и расходовать диск, строки БД и резервные копии. Ограничение регистрации это не предотвращает.

Одна лишь проверка свободного места без атомарной квоты не устраняет гонку.

## 3. P1 — PDF timeout не ограничивает фактическую работу Chromium

Код: [PlaywrightArticlePdfRenderer.cs](../src/GaifulinLab.Infrastructure/Pdf/PlaywrightArticlePdfRenderer.cs), строки 46–55, 111–145.

`CancelAfter(settings.Timeout)` отменяет токен, но вызовы `NewContextAsync`, `SetContentAsync`, `AddScriptTagAsync`, `EvaluateAsync` и `PdfAsync` не связаны с этим токеном. Ожидание render slot начинается ещё до создания timeout. Отмена токена сама по себе не прекращает зависший рендер и не закрывает browser context.

`EvaluateAsync` ожидает завершения возвращённого Promise, в данном случае MathJax и шрифтов; это соответствует [документации Playwright](https://playwright.dev/dotnet/docs/api/class-page#page-evaluate). При зависании задача может удерживать render slot и остановить обработку очереди единственным worker. Это дефект надёжности; воспроизводимый вредоносный документ в рамках аудита не подбирался.

Исправление: общий deadline от входа в рендер, ограниченная очередь ожидания и принудительное закрытие соответствующего context при timeout/cancellation. Простого `WaitAsync(token)` без прекращения браузерной операции недостаточно. Отдельно ограничить объём итогового HTML и суммарных embedded media: сейчас лимит проверяется для каждого asset, а повторяющиеся ссылки многократно вставляют base64 одного изображения.

Эти зависимости есть только в отдельном worker-образе. Compose также не передаёт их в API.

Для описанного контейнерного развёртывания прямой endpoint не сможет успешно отрендерить PDF и должен завершиться ошибкой renderer. Это статический вывод по Dockerfile, без сборки образа. Тест endpoint проверяет только 401/403, успешный admin-запрос отсутствует.

Исправление: направить этот сценарий в PDF worker либо включить полный набор зависимостей в API-образ. Добавить smoke test успешного рендера на собранном образе.

## 5. P2 — удалённая статья навсегда занимает позицию в серии

Код: [DeleteArticleCommandHandler.cs](../src/GaifulinLab.Application/Articles/DeleteArticle/DeleteArticleCommandHandler.cs), строка 22; [Series.cs](../src/GaifulinLab.Domain/Series/Series.cs), строка 117; [ArticleSeriesConfiguration.cs](../src/GaifulinLab.Infrastructure/Persistence/Configurations/ArticleSeriesConfiguration.cs).

Удаление выставляет только `DeletedAt`. Связь `article_series` остаётся, а проверка занятой позиции учитывает все связи. После удаления API запрещает менять taxonomy удалённой статьи, поэтому освободить позицию через обычный CRUD уже нельзя.

Воспроизведено через API: назначить статье позицию 1 → удалить статью → назначить другой статье ту же позицию. Последний запрос возвращает 400 с `Series position 1 is already occupied`.

Исправление: при удалении освобождать связи серии в той же транзакции либо вводить согласованную модель архивных связей. Простая фильтрация удалённых статей в запросе недостаточна: остаётся уникальный индекс `(SeriesId, Position)`.

## 6. P2 — сохранение статьи не защищено от потери изменений

Код: [UpdateArticleLocalizationCommandHandler.cs](../src/GaifulinLab.Application/Articles/UpdateArticleLocalization/UpdateArticleLocalizationCommandHandler.cs), строки 38–61; [ArticleLocalizationConfiguration.cs](../src/GaifulinLab.Infrastructure/Persistence/Configurations/ArticleLocalizationConfiguration.cs); [UpdateArticleLocalizationRequest.cs](../src/GaifulinLab.Contracts/Articles/UpdateArticleLocalizationRequest.cs).

Запрос передаёт содержимое без ожидаемой версии, `UpdatedAt` не является concurrency token, ETag/If-Match отсутствует. Две вкладки могут прочитать одну версию; сохранение устаревшего текста из второй вкладки перезапишет более свежий текст первой, и оба запроса будут успешными.

Статический вывод. Исправление: вернуть клиенту версию локализации, требовать её при обновлении и проверять при записи. Конфликт должен возвращать 409/412 и позволять пользователю сохранить обе версии текста. Проверка только серверной версии, загруженной в начале каждого PUT, не обнаруживает устаревшую вкладку: нужна версия от клиента.

## 7. P2 — публичный список читает весь контент всех переводов

Код: [GetPublicArticlesQueryHandler.cs](../src/GaifulinLab.Application/Articles/Public/GetPublicArticles/GetPublicArticlesQueryHandler.cs), строки 60–61, 88; [GetAdminArticlesQueryHandler.cs](../src/GaifulinLab.Application/Articles/GetAdminArticles/GetAdminArticlesQueryHandler.cs), строки 19–21.

Публичный список делает `Include(article => article.Localizations).ToListAsync()` без пагинации. Загружаются все подходящие статьи, все их локализации и полные Markdown-тексты, хотя DTO списка не содержит Markdown. Сортировка публичного списка выполняется после загрузки в память. Административный список также читает полный контент.

Это не утечка черновиков в HTTP-ответ: DTO их не возвращает. Это неограниченные затраты на чтение и память, включая ненужные переводы и черновики. При росте числа статей стоимость одного анонимного запроса растёт вместе со всей базой контента.

Исправление: SQL-проекция полей DTO, фильтрация нужной локализации, сортировка и ограничение страницы в БД; taxonomy загружать только для текущей страницы. Дополнительно `GetAdminArticleQueryHandler` загружает три коллекции через sibling Include: возможное перемножение строк следует убрать проекцией или split query с учётом нужной согласованности данных.

## 8. P2 — ограничения длины проверяются только базой данных

Код: [ArticleLocalization.cs](../src/GaifulinLab.Domain/Articles/ArticleLocalization.cs), строки 58–71; [ArticleLocalizationConfiguration.cs](../src/GaifulinLab.Infrastructure/Persistence/Configurations/ArticleLocalizationConfiguration.cs), строки 33–38; [ApiExceptionFilter.cs](../src/GaifulinLab.Api/Filters/ApiExceptionFilter.cs), строка 21.

Для Title/Slug/Summary заданы ограничения БД 300/200/1000, но API-контракты и доменная нормализация длины не проверяют. Например, Title из 301 ASCII-символа доходит до PostgreSQL, вызывает ошибку записи, после чего фильтр представляет её как 409 `persistence_conflict`. Пользователь не получает сообщения о слишком длинном заголовке. Аналогичная проблема у тегов длиной более 100 символов.

Статический вывод по схеме и обработчику; PostgreSQL не запускался. `HasMaxLength` не выполняет клиентскую валидацию до передачи данных провайдеру — см. [документацию EF Core](https://learn.microsoft.com/en-us/ef/core/modeling/entity-properties#maximum-length). InMemory-тесты это ограничение не проверяют.

Исправление: единые лимиты валидации API/Domain и схемы, понятные ошибки полей с 400. Обрабатывать как conflict только ожидаемые ограничения/конкурентные изменения; прочие ошибки БД логировать и классифицировать отдельно.

## 9. P2 — null внутри массива Series вызывает HTTP 500

Код: [UpdateArticleTaxonomyCommandHandler.cs](../src/GaifulinLab.Application/Articles/UpdateArticleTaxonomy/UpdateArticleTaxonomyCommandHandler.cs), строка 103.

Воспроизведено: `PUT /api/admin/articles/{id}/taxonomy` с `{"topicIds":[],"series":[null],"tags":[]}` под владельцем статьи возвращает 500. Проверяется сама коллекция, но не её элементы; `item.SeriesId` вызывает NullReferenceException. Nullable-аннотация типа не гарантирует отсутствие null во входном JSON.

Исправление: проверять элементы коллекции до LINQ, возвращать 400 с указанием поля/индекса. Ограничить также длины коллекций до запросов к БД.

## 10. P2 — загрузка проверяет сигнатуру, но не валидность изображения

Код: [UploadMediaCommandHandler.cs](../src/GaifulinLab.Application/Media/UploadMedia/UploadMediaCommandHandler.cs), строки 120–122.

Воспроизведено: файл `broken.jpg` с MIME `image/jpeg` и содержимым из трёх байтов `FF D8 FF` получает 201. Файл не является декодируемым JPEG, но сохраняется и публикуется. Для остальных форматов тоже проверяется только короткий заголовок, лимитов ширины/высоты/числа пикселей нет.

Подтверждён дефект валидации, а не XSS или выполнение загруженного кода. Потенциальные последствия: битые картинки и неконтролируемые затраты декодирования специально подготовленных изображений браузером/PDF worker.

Исправление: валидировать структуру изображения подходящим декодером с ограничениями ресурсов, проверять размеры и допустимость анимации; при необходимости нормализовать изображение повторным кодированием.

## 11. P2 — истёкший PDF worker может перезаписать результат нового worker

Код: [PdfExportWorker.cs](../src/GaifulinLab.Infrastructure/Pdf/PdfExportWorker.cs), строки 61, 98–106, 120–130.

Повторный захват задачи после истечения lease предусмотрен. Но `Complete` обновляет строку только по Id, а `FailAsync` проверяет только общий статус Processing: сохранённый `AttemptCount` не сравнивается с номером попытки обрабатывающего worker.

Сценарий при двух worker: попытка A работает дольше lease → B захватывает ту же задачу → A позднее завершает её или помечает failed. A может изменить состояние, которым уже владеет B, либо перезаписать готовый результат. Дефект timeout увеличивает вероятность. При единственном worker это конкурентное условие не возникает.

Статический вывод. Исправление: атомарные условные обновления по `(Id, AttemptCount, Status)` или уникальному lease token, проверка числа затронутых строк, очистка результата проигравшей попытки. При длительном рендере — продление lease.

## 12. P2 — внешний nginx не согласует лимит загрузки с API

Код: [host-reverse-proxy.conf](../deployment/nginx-host/host-reverse-proxy.conf), строка 33; [gaifulinlab.conf](../deployment/nginx-web/gaifulinlab.conf), строка 38.

Внутренний nginx задаёт `client_max_body_size 11m`, API допускает файл 10 MiB, а внешний nginx лимит не задаёт. При стандартной конфигурации хоста наследуется [nginx default 1m](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size): корректная загрузка, например изображения 2 MiB, получит 413 ещё до API.

Это условная проблема развёртывания: повышенный глобальный лимит в конфигурации конкретного хоста может её скрывать. Исправление: явно согласовать лимит на внешнем proxy в конфигурации этого сайта и проверить upload через полный публичный маршрут.

## 13. P2 — API-тесты влияют друг на друга через rate limiter

Код: [AuthEndpointsTests.cs](../tests/GaifulinLab.Api.Tests/Authentication/AuthEndpointsTests.cs), строки 22, 312; [AdminArticleEndpointsTests.cs](../tests/GaifulinLab.Api.Tests/Articles/AdminArticleEndpointsTests.cs), строка 19.

`IClassFixture<AuthWebApplicationFactory>` переиспользует приложение в пределах класса, все запросы получают loopback IP. Независимые тесты исчерпывают один и тот же лимит login/register. В полном запуске воспроизведены два падения с 429; при запуске только этих двух тестов оба проходят.

Исправление: изолировать экземпляр limiter/приложения или IP между сценариями; тесты лимитов держать на отдельном приложении с реальной политикой. Дополнить InMemory-набор небольшим PostgreSQL integration-набором для SQL просмотров, уникальных индексов, миграций и lease-захвата PDF.

## 14. P3 — неуспешное создание файла может удалить ранее существовавший файл

Код: [FileSystemMediaStorage.cs](../src/GaifulinLab.Infrastructure/Media/FileSystemMediaStorage.cs), строки 38–47.

`FileMode.CreateNew` правильно отвергает существующий путь, но общий catch безусловно вызывает `File.Delete(fullPath)`. Поэтому ошибка «файл уже существует» удаляет файл, который этот вызов не создавал.

Воспроизведено на временном файле: успешный SaveAsync → второй SaveAsync того же пути бросает IOException → OpenReadAsync возвращает null. В обычном upload пути случайные, поэтому непосредственная достижимость через API мала; это дефект контракта storage, опасный для повторных записей и будущих вызывающих компонентов.

Исправление: удалять только файл, созданный текущим вызовом; отделить успешное открытие CreateNew от очистки после неудачного копирования либо писать во временный файл с атомарным переносом.

## Дополнительные наблюдения

- Публичный GET статьи заново выполняет Markdown parsing, syntax highlighting и sanitization; кэша по версии локализации нет. Счётчик просмотров также пересчитывается через LongCount. Это кандидаты для профилирования после устранения неограниченных выборок.
- Публичный POST views не ограничен по темпу и каждый раз выполняет обращения к БД, даже для уже учтённого посетителя. ON CONFLICT корректно устраняет дубли, но не стоимость запросов.
- PDF exports сохраняют snapshot Markdown и файлы без механизма retention/очистки. Доступ только администраторам уменьшает риск злоупотребления, но обычные повторные выгрузки также накапливают данные.
- Фильтр превращает любые InvalidOperationException в 400 и возвращает их Message; это смешивает доменные ошибки с внутренними сбоями и может раскрывать технические подробности. Лучше выделить доменные исключения, а неожиданные ошибки логировать с correlation id и возвращать нейтральный 500.
- Само название `/api/admin/articles` не означает отсутствующую проверку роли: текущая модель явно разрешает авторский workspace обычным пользователям. Проверки OwnerUserId и DeletedAt в основных CRUD handlers присутствуют; чтение/изменение чужих статей через эти handlers не подтверждено.
- Используются sanitization HTML, параметризованный SQL для просмотров, проверка доверенных proxy networks и защита storage path от выхода за корень. Эти механизмы полезны, но не заменяют проверки выше.

## Порядок исправления

1. Lockout и ресурсные ограничения media/Markdown/PDF; исправить фактический timeout и контракт выполнения PDF.
2. Освобождение позиций при удалении, проверка версии при сохранении, условное завершение PDF lease.
3. Пагинация/проекции, входная валидация, конфигурация внешнего nginx.
4. Изоляция тестов, PostgreSQL/container smoke tests, storage cleanup и retention.
